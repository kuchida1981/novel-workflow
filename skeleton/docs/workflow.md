# Novel Workflow (NW) v0.4 — 運用マニュアル

## 概要

Novel Workflow (NW) は、ソフトウェア開発のプラクティス（設計・実装・レビュー）を小説執筆に適用したフレームワークです。上流工程の決定事項を下流工程の制約として扱うことで、大規模な物語でも一貫性を維持します。

v0.4 では、三者協業モデル（ユーザー / Claude Code / agy）と統一ループを導入し、物理的に異なるシステムによる役割分離を実現しています。

---

## 役割の定義（三者協業モデル）

| 役割 | 担当 | 責任 |
| :--- | :--- | :--- |
| **監督 (Director)** | **ユーザー** | アイデア出し、最終レビュー、承認ゲート |
| **オーケストレーター** | **Claude Code** | 素案の提案、agy への指示準備、レビュー（面白さ含む）、コンテキスト管理 |
| **筆者 (Writer)** | **agy** | 成果物の執筆（全5ステップ）、git commit |

---

## ライフサイクルの全体像

```
Step 1: 核 (Core)
  ↓ [統一ループ: 設計→執筆→レビュー]
Step 2: 素材 (Assets)
  ↓ [統一ループ: 設計→執筆→レビュー]
Step 3: 構造 (Plot)
  ↓ [統一ループ: 設計→執筆→レビュー]
Step 4: シーン (Scenes)
  ↓ [統一ループ: 設計→執筆→レビュー]
Step 5: 本文 (Draft)
  ↓
振り返り (Post-mortem)
```

### 統一ループ（全ステップ共通）

各ステップは以下の3フェーズで進行する。

**Phase 1: 設計 (User × Claude Code)**
1. ユーザーがアイデア・方向性を提示する。
2. Claude Code が素案を整理・提案する。
3. 対話で合意を形成し、agy への指示内容を確定する。

**Phase 2: 執筆 (agy via MCP)**
1. Claude Code が agy に上流成果物と合意事項を含むプロンプトを送信する。
2. agy が成果物を生成し、git commit する。

**Phase 3: レビュー (User × Claude Code)**
1. Claude Code が diff をレビューし、所見をユーザーに提示する。
2. ユーザーが承認またはリテイクを判定する。
3. リテイク時は Phase 1（方向性の見直し）または Phase 2（修正指示で再執筆）に戻る。

## 執筆・フォーマット規約

### 1. Markdownソースの書式
- **字下げ禁止:** 段落行頭に全角スペースを挿入しないこと。日本語の字下げは組版段階で制御すべきものであり、テキストレベルでは不要。
- **改行:** 原則として、一段落ごとに1行の空行を入れる。

### 2. 表現技法（Aesthetics & Writing）
- **Show, Don't Tell (描写による提示):** 感情や状況を地の文で「説明（Tell）」するのではなく、キャラクターの行動や五感（Show）を通じて読者に伝える。
- **過剰要約の排除:** シーンが既に描写している内容を、語り手が再度要約して説明することを避ける。
- **リサーチの先行:** 専門的な小道具（自転車、酒、衣装、専門用語など）が登場する場合、執筆前にリアリティの精査を行う。

## Git・ブランチ戦略

### ブランチ命名規則

```
work/<project-name>    # 作品ごとのトピックブランチ
feature/<change-name>  # フレームワーク変更（OpenSpec change）
```

### PR 常時オープン運用

1. **作品開始時:** ブランチ作成後、draft PR をオープンする。
2. **目的:** 進捗の可視化、マルチ端末からのアクセス。
3. **マージ = 作品の完成:** 全ステップ完了・最終承認後にマージする。中間マージは原則なし。

### コミットルール

1. **agy がコミット:** 成果物を生成した時点でコミットする（レビュー前に記録）。
2. **対象ファイルのみ:** `git add <対象ファイル>` のみ使用。`git add -A` や `git add .` は禁止。
3. **品質チェックの厳守:** `git commit` 時に `--no-verify` を使用してはいけない。

## 各ステップの詳細

### Step 1: 核 (Core) — `artifacts/01_core/core.md`
**目的:** 物語の根幹となるテーマ・問い・前提を定義する。
**完了条件:** `core.md` の全項目が記述され、監督が承認を宣言する。

### Step 2: 素材 (Assets) — `artifacts/02_assets/`
**目的:** Core のテーマを体現するキャラクターと世界観を設計する。
**成果物:** `characters/<name>.md`, `world.md`
**完了条件:** 主要設定が記述され、監督が承認。

### Step 3: 構造 (Plot) — `artifacts/03_plot/plot.md`
**目的:** 物語の骨格（章構成・サマリー）を設計する。
**制約:** Core および Assets と矛盾しないこと。

### Step 4: シーン (Scenes) — `artifacts/04_scenes/`
**目的:** 各章をシーン単位に分解し、執筆仕様を定義する。

### Step 5: 本文 (Draft) — `artifacts/05_draft/`
**目的:** Scenes の仕様に従い、本文を執筆する。
**完了条件:** 全シーンの本文が完成し、監督が承認。

## バックトラック・ルール
下流工程で上流の変更が必要になった場合、以下の手順を踏みます。
1. **変更の宣言:** 「Step X の〇〇を変更したい」と明示。
2. **影響範囲の特定:** 変更対象より下流の全ステップへの影響を確認。
3. **最小限の修正 & 再承認:** 修正を行い、改めて承認ゲートを通過する。

大規模なバックトラックは OpenSpec change として管理することを推奨。
